# 实际返利（0.1.5）

## 使用方式

在「报单」列表点击「调整返利」，对该报单的每个商品项设置实际返利：

0.1.5 也可直接从「快递」列表点击「调整返利」，**已结单的快递同样保留此入口，无需撤销结单**。若快递包含多个来源报单，先选择对应报单，再调整该快递涉及的商品批次；同一报单里没有出现在此快递中的商品不会被带入表单。普通「编辑报单」中的预计返利仍是原始预估，不等于这个独立的实际返利调整功能。

- 默认「按预计全额」，实际返利随预计返利变化，无需给旧数据补字段。
- 自定义金额允许为 0，也允许高于预计值；负数、超过两位小数或不安全的整数金额会被拒绝。
- 可恢复「按预计全额」。修改报单的其他内容不会覆盖已设置的实际返利。
- 商品已经出库、退款或对应快递已结单时，仍可单独调整实际返利。名称、数量、付款、预计返款等原有锁定规则不变。

输入金额的口径与预计返利一致：**原始整批商品的总返利，不是单件金额，也不是退货后剩余部分的净返利。** 系统按未退款数量计算计入利润的份额，弹窗会显示已退款数量和最终计入金额。

从快递进入时也不是只修改该快递的分摊金额：如果同一商品批次被拆到多笔快递，修改原整批返利后，这些快递的返利分摊会一起更新。结单状态、已登记的实际返款、快递费用与出库数量均不改变。

例：一项报单有 4 件商品，原整批预计返利 40 元。设实际总返利为 20 元，若其中 1 件退款，最终计入利润的是 15 元。若全退，计入金额为 0。剩余库存和多个快递的分摊均按分处理，合计保持一致。

## 统计口径

预计返利仍保留作对照，预计收益仍按预计返款 + 预计返利计算。

利润 = 已结单实际返款 + 未结单预计返款 − 商品付款 + 实际返利

纯利润 = 利润 − 快递费用；利率 = 纯利润 ÷ 商品付款。

这里的实际返利包含“默认按预计全额”以及手动确认的金额，**不是收款流水或已到账的证明**。市场实际返款仍独立登记，不把返利重复算入返款金额。

## 同步与兼容

- `reportItems.actualRebateCents` 是可选的非负安全整数分；缺省（或兼容快照中的 null）回退 `expectedRebateCents`。schemaVersion 保持 1，SQLite 无需改表，旧队列与 opId 不重写。
- 修改使用独立 `report.rebate.update` 操作：`{ id: reportId, items: [{ id: reportItemId, actualRebateCents: 0 }] }`。同一操作内的多项修改原子完成；传 null 恢复默认。
- 不能把实际返利偷偷附加到旧 `report.create/update` 请求。旧服务不认识新的独立操作时会明确拒绝，客户端保留本地修改和失败队列，不会显示已成功保存到服务端。
- 后端至少需要支持 0.1.4 的返利操作；0.1.5 的快递快捷入口复用同一操作，无需迁移数据。建议安装最新 APK；早于 0.1.4 的 APK 虽然能保留未知字段，利润显示仍按旧的预计返利计算，请勿混用。网页需要刷新获取新资源。
- 若此前已向旧服务提交过返利操作，先升级后端，再在设置里选择该失败操作的「换新编号重试」。不能重用已被服务器拒绝并记录的 opId。
- 升级前建议导出本机备份；服务器发布前保留数据库副本。同签名覆盖安装 APK，不要卸载或清除本机数据。

## 同时修复的问题

1. 快递编辑用普通对象按商品名汇总时，`__proto__`、`constructor`、`toString` 等商品名可能丢失。现在用 Map 汇总并回归这些名称。
2. 修改或作废前序未结单快递，可能改变后续已结单快递的 1 分钱分摊。现在逐条保护已结单分摊；确实会改变金额时，要求先撤销相关结单。无金额影响的修改仍可进行。
3. 接近安全整数上限的金额，原先除以 100 再格式化可能使重新保存后的值相差 1 分。现在按整数十进制拆分元和分，保留原金额，也支持负利润显示。
4. 网页升级后，浏览器或中间缓存仍可能提供旧脚本。现在核心静态资源及 Service Worker 使用一致的版本参数，HTML、脚本、样式和 manifest 要求重新验证缓存，避免刷新后仍看不到新功能。
5. Android 本地 `file:///android_asset/` 地址的空 authority 曾被误判为外部地址。现在接受合法本地导航及资源版本参数，同时继续拒绝外部地址和目录逃逸；启动地址、存储来源不变。

后续升级网页资源时，应同步更新 `public/index.html`、Service Worker 注册地址和 `public/sw.js` 的资源版本及缓存名称；一致性测试会检查它们，再通过 `npm run build:web` 和 Android 构建同步派生文件。CDN 可能覆写源站缓存头，因此不能只依赖 `no-cache`；发布后应核对首页引用和带版本参数的公网资源内容。
